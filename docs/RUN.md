# 실행 안내 — 품질 회수·공급 복구 운영 시스템 (W03)

가상기업 기준일 **2026-07-01**. 설계 근거: `docs/team/01_설계안.md`(v1.1), `docs/analysis/01_영향분석.md`, `docs/analysis/02_원인조사.md`. 검수 수정 반영: `docs/team/03_수정목록.md` F1~F17.

## 0. 운영 원칙 — 비용 0원, 모의 AI 고정

- **운영은 비용 0원 원칙으로 모의 AI(규칙·템플릿)로 고정한다.** 실제 Claude API는 호출하지 않는다.
- Claude API 호출 경로(`src/ai.js`)는 구현돼 있으나 **운영에서 미사용·미검증**이다. 실제 API로 한 번도 호출해 보지 않았고, 모의 클라이언트를 주입한 단위 테스트로 요청 파라미터·거절·오류 처리만 확인했다.
- 안전장치(F17): Claude API 경로는 `ANTHROPIC_API_KEY`가 있고 **동시에** `AI_REAL_ENABLED=true`일 때만 열린다. 둘 중 하나라도 없으면 무조건 모의 AI이며 SDK 클라이언트도 만들지 않는다. 운영 환경에는 두 값을 설정하지 않는다.
- 모의 AI는 입력(판정 수치·민감도·회신 문장·대안 계산 결과)에 따라 출력이 달라지고, 그 출력은 사람이 확정·선택해야만 처리에 쓰인다(회신 분류는 미리 선택되지 않음, 대체 공급 안내 초안은 담당자가 선택 적용).

## 1. 실행

```bash
npm ci            # 의존성: @anthropic-ai/sdk, zod (새 의존성 없음)
npm start         # http://localhost:3000 (PORT 환경변수로 변경, 배포는 8080)
npm test          # node --test — 57건(규칙·시나리오 3종·확장 ON/OFF·모의 AI·재공급·검수 수정 F1~F24 재현)
```

- Node.js 22 이상(배포: Docker `node:22-alpine`, 기존 Dockerfile 그대로). `.dockerignore`로 node_modules·state.json·원본 폴더·기록 키 폴더를 이미지에서 제외.
- 상태: 서버 메모리 + `data/state.json`(없으면 시드에서 생성). 재시작해도 이어서 동작.
- 상태를 바꾸는 요청이 실패(400·409·422·500)하면 서버가 요청 전 상태로 되돌린다(부분 반영 없음). 잘못 인코딩된 주소는 400, 없는 주소는 404, 예상하지 못한 예외는 500(한국어)으로 응답하고 서버는 계속 동작한다(F18).
- 고객 보유 수량 회신은 해당 고객의 회수 배치 SBL 출하량을 넘으면 400(F22).
- 상태를 바꾸는 요청(POST)은 본문을 끝까지 읽은 뒤 한 번에 하나씩 처리하고, 되돌리기 스냅샷은 상태 변경 직전에 찍는다 — 실패한 요청이 다른 성공 요청의 기록을 지우지 않음(F23). 예상하지 못한 예외로 안전망이 작동하면 마지막 저장 state.json을 다시 읽는다(F24).
- 초기화: 화면 상단 `초기화` 또는 `POST /api/reset`.
- 원본: `data/source/`(대회 원본의 필요한 파일만 무수정 복사, `data/source/README.md` 참고).

## 2. 환경변수

| 이름 | 뜻 |
|---|---|
| `PORT` | 서버 포트(기본 3000, 배포 8080) |

## 5. 통제 규칙(검수 수정 반영)

| 규칙 | 동작 |
|---|---|
| J3 의결 효력 | 고객 통지 발송·재공급 계획 계산·상신·승인·회수 작업 완료는 "가장 최근 상신이 승인"이고 사건이 의결 이후 단계일 때만 가능. 재상신~회신 사이, 재검증 필요, 보류, 거절 상태에서는 409 |
| 거절 / 추가자료 요구 | 의결 배치 목록 비움. 거절 → 의결 기반 작업 취소(발송된 통지가 있으면 정정 통지·영업 확인 작업), 추가자료 → 재검증 필요. 거절 후 재상신은 "거절 사유 검토" 작업 완료 후 |
| 순서 | 판정 전 상신 409, 이미 의결된 사건 재상신 409(판정 변경 시에만), 같은 배치 중복 사건 접수 409 |
| 계획 재검증 | 재검증 필요 계획은 회신 이벤트로 자동 재계산하지 않음. 승인된 계획을 다시 계산하면 이전 버전(승인 기록) 보존, 새 버전은 재승인 필요, 이전 계획 기반 작업은 재검증 필요 |

| 입력 검증 | 날짜 YYYY-MM-DD, 수량 0 이상 정수, 가정값 양수, 고객은 회수 범위 안, 확인요청은 선택지, 승인 결정은 승인/반려만 — 위반 시 400, 상태 무변경 |
| 통지 | 발송 전 금지 표현 서버 점검(원인 단정·보상 금액·%·미확정 납기·언론/방송/SNS·예방 점검 배치). 발송 완료 통지는 수정·재발송 불가 |
| 확장(a) | 의결 시점 설정을 사건에 기록. OFF로 의결하면 N8에 "예방 점검 미수행(위험)" 표시. 의결 후 ON으로 바꾸면 빠진 로트 격리·예방 점검 작업 보충 생성 |

## 8. 알려진 한계

- **공유 상태**: 서버 상태가 하나라, 한 사람이 시나리오 시작·초기화·확장 토글을 하면 같은 배포본을 보는 모든 사용자의 화면이 바뀐다(확인창·상단 안내로 알림, 사용자별 분리는 미구현).
- 재공급 일정은 [가정] 입력 기반 모의 계산(영업일 생산, 기존 주문은 예상 납기 순, 기준일 이후 신규 주문 미반영). 원료 가용량 부족은 경고만.
- 미확정 클레임 = `status ∈ {접수, 조사중, 정정(재조사)}` 이고 `defect_confirmed=False` [가정]. 확정·미확정이 함께 있는 배치는 `조사·소명` 우선 표시.
- 예방 점검 트리거는 `회수 대상` 배치만. 로트 잔량은 수치 대신 확인요청.
- 출하 정지·로트 격리는 작업으로만 관리(실제 출하 시스템 차단 없음).
- 사용자 인증·권한 구분 없음(승인자는 화면 선택값).
