## 1. 회수 판정 재계산

### 1.1 방법
- 도구: Python 3 (`python -I`, 표준 라이브러리 csv만 사용). 구분자 `|`, UTF-8. 스크립트는 세션 임시 폴더에서 실행했다(아래 핵심 로직 참고).
- [원본] 정의(`calculation_definitions.md` 1.9): `Batch Defect Rate = 규격이탈확정 수량 / 배치 수량`, `회수 대상 = (defect_confirmed=True) AND (rate ≥ 10%)`.
  분자 = `qc_claims_cv.defect_confirmed=True`인 행의 `qty_affected` 배치별 합계.
  분모는 원문에 "`prod_batch_log_cv` / `shipment_batch_link_cv`"로 **두 가지가 같이 적혀 있다**.
- 계산: 배치 480개 전체를 대상으로 했다. 분모 P는 `produced_qty`, 분모 S는 SBL `shipped_qty`의 배치별 합계다. 미확정(False) 수량을 더한 "잠재율"도 따로 계산했다.

```python
conf[b] = sum(qty_affected for claim in qc if claim.batch_id==b and claim.defect_confirmed=='True')
unc[b]  = sum(qty_affected ... defect_confirmed=='False')
rateP = conf/produced_qty ; rateS = conf/sum(SBL.shipped_qty) ; potential = (conf+unc)/produced_qty
```

### 1.3 분모 차이와 팀 권고

| 값의 안정성 | 생산 완료 시 고정 | 출하가 추가될 때마다 변동. 출하/생산 비율 83.2~99.96%, 평균 94.8% |

| 정의 문구 | "배치 수량"에 직접 대응 | 같은 원문에 병기 |

**[가정·팀 권고]** 판정에 쓰는 분모는 **생산량(`produced_qty`)**으로 한다. 이유는 세 가지다. ① 정의식 문구 "배치 수량"에 직접 대응한다. ② 모든 배치에서 계산할 수 있다. ③ 판정 시점에 값이 바뀌지 않아 재현할 수 있다.
출하량 기준 율은 **보조 지표로 함께 표시**한다. **두 분모의 판정이 다르면**(생산 기준 미달, 출하 기준 충족) 자동으로 "대상 아님" 처리하지 않는다. 이 경우 `분모 민감` 플래그를 달고 품질위원회에 두 값을 같이 상신한다. 회수 결정권이 위원회에 있고, 원문이 두 분모를 모두 언급하기 때문이다.

### 3.3 직접 원인 vs 과정상 원인
- **직접 원인(제품 불량을 일으킨 물리적 요인): 미확정.** 가설은 H1·H2·H3이고, 현재 증거는 "로트 단독"보다 "로트 + 배치 요인" 쪽에 무게가 있다. 확정하지 않는다.
- **과정상 원인(통제 실패): 데이터로 확인되는 사실** [도출]
  1. **보류 로트의 생산 투입**: 검사 결과 "보류"(02-09) 이후에도 3개 배치에 투입됐다. 보류 로트 사용 승인 기록은 원본에 없다(미확인).
  2. **합격 로트 있는데 보류 로트 사용**: 03-16 B-02-2603-01 생산 시 LOT-B-2603-1(03-10 입고, 규격내)이 이미 있었다.
  3. **배치 판정 "보류" 배치의 출하**: 두 배치 모두 qc_result=보류인데 SBL상 생산 4~5일 뒤(02-09, 03-20)부터 출하됐다. 출하 승인 기록은 원본에 없다(미확인).
  4. 입고 전 투입(02-05 < 02-06)은 A05의 알려진 기록 한계와 같은 패턴이다(§4). 투입 이력 480건 중 213건이 이런 사례라 **통제 실패의 증거로 쓰지 않는다.**
- [원본] 정책상 회수는 인과 규명을 기다리지 않는다("원인 조사는 회수와 별도 트랙"). 따라서 위 가설은 **회수 판정에 입력하지 않고**, 조사 트랙과 재발 방지(로트 사용 통제) 작업으로만 연결한다.

## 6. 앱 설계 의견 — **조건부 동의**

### 6.1 찬성 (근거)
- Case 중심 연결은 데이터 구조와 맞는다. 클레임·배치·로트·소비 키가 100% 일치하고(§2.3), 배치→SBL→고객 연결이 원본으로 가능하다. 회수 사건 하나에 배치 2개를 같은 로트로 묶는 구성이 실제 데이터로 작동한다.
- 규칙 엔진과 사람 의결의 분리는 정책·권한 문서와 일치한다(판정 = 결정적 규칙, 실행 = 품질위원회).
- (a) 로트 추적은 원본만으로 **확장 유무 차이를 보여줄 수 있다**. 확장이 없으면 B-02-2602-02·03(SBL 302,581 EA, 고객 C-101·102·103)이 보이지 않는다. 확장이 있으면 예방 점검 대상으로 분리되고 점검 작업이 생성된다. A01의 "필수 확장의 실제 반영" 요건을 원본 근거로 충족한다. **필수 확장으로 (a)를 권고한다.**

### 6.2 우려
1. **AI가 판정에 개입할 위험.** 판정은 규칙 엔진 단독으로 하고, AI 출력은 판정 필드를 바꿀 수 없게 설계해야 한다. 근거 요약에서도 원인을 "확정"으로 표현하지 못하게 해야 한다.
2. **로트 추적 결과를 회수 대상으로 확대하면 안 된다.** B-02-2602-02·03은 확정 불량 0건이라 정책상 회수 대상이 아니다. 별도 상태("예방 점검/조사·소명")로 두고, 처리 결정(출하 보류·재검사)은 품질팀 사람이 한다. 과잉 대응(W03 질문)을 막는 지점이다.
3. **분모 정의가 없다.** §1.3 권고(생산량 판정 + 출하량 보조 + 분모 민감 플래그)를 규칙에 넣어야 한다. 그렇지 않으면 변경 사례 ②가 재현되지 않는다.
4. **회수 범위의 근거 수준을 구분해야 한다.** 고객·수량은 SBL [원본]이다. 금액·주문 영향은 SH와 연결할 수 없어 [가정/합성]이다. C-105 불일치는 [미확인]이다. 화면에서 이 셋을 구분하지 않으면 A05 위반이다.
5. **(b) 캐파 기반 재공급 일정의 데이터 근거가 약하다.** 캐파 기간 단위가 원본끼리 모순이고(G11), 재고·리드타임·재승인 이력이 없다(W03 미해결). L-02 가동률 97%와 M-B 단일 독점 공급(V-205)은 **제약으로 반영할 가치가 있다**. 하지만 산출 일정은 전부 가정 기반 모의다. 필수 확장을 (b)로 삼으면 "유리한 가정으로 만든 성과" 지적(A01·A05)을 받을 위험이 있다.
6. 위원회 회신 상태가 "승인"만 있으면 사례 ③을 보여줄 수 없다. **승인 / 추가자료 요구 / 거절(조사 계속) / 정정 후 재상신** 상태가 필요하다.

### 6.3 대안·조건 (동의 조건)
- C1. 필수 확장 = (a) 로트 추적 → 예방 점검 대상 분리. **실제 작동 + 확장 유무 비교 화면.**
- C2. (b)는 "추가 확장(모의)"으로 둔다. 파라미터(잔여 캐파 비율, M-B 리드타임, 재승인 소요일)는 **사용자가 입력하는 명시적 가정**으로 노출한다. 가정이 바뀌면 일정이 다시 계산되게 해서 다른 부서(생산 L-02 97%, 조달 V-205 독점) 제약이 계획을 바꾸는 지점으로 쓴다. 부서 영향 요건(R5) 충족용.
- C3. 규칙: `rateP ≥ 10%` = 회수 대상, `rateP < 10% ≤ rateS` = 분모 민감(상신), 미확정 = 조사·소명, 언론 = 기록만. 판정이 정정되면 후속 작업을 자동으로 "재검증 필요"로 바꾼다.
- C4. 사건 레코드에 미확인 목록(C-105 귀속, 고객 잔량, 보류 사용 승인 기록)과 각 확인 요청 작업을 연결한다.
- C5. 원인 조사 트랙은 별도 상태 머신으로 둔다(가설 H1~H5와 확인 작업). 회수 판정과 상태를 공유하지 않는다.

**결론: 조건부 동의.** 조건 C1~C5가 반영되면 동의한다. 특히 C1(필수 확장은 (a))과 C3(분모 규칙)이 빠지면 반대한다.
